# Common Pitfalls

Lessons learned from code review cycles. Check these before submitting changes.

## Core-First Architecture

- **Never reference `@guren/server` in docs or user-facing code.** Use `@guren/core` for all imports. The `audit:core-first` script catches this.
- **When adding exports to `@guren/server`**, they are auto-available from `@guren/core` (via `export *`). No need to touch core's index.
- **When adding ORM exports**, they must be explicitly listed in `packages/core/src/index.ts` (allowlist, not `export *`).
- **Don't reference non-existent symbols in docs.** Verify imports compile before documenting them.

## Stale Build Artifacts

- **A stale `dist/` can fail tests silently, not just loudly.** The documented symptom is a DTS build error (`could not find declaration file`), but a stale artifact can also load fine and merely *lack a field added since it was built* — which surfaces as a confusing `toEqual` mismatch in an unrelated package's unit test.
- **`packages/cli` tests reach `@guren/server` through `dist/`, not `src/`.** `@guren/core` resolves to `packages/core/src/index.ts`, but its `export * from '@guren/server'` follows the workspace symlink to `packages/server`'s `exports`, which points at `dist/index.js`. So anything a CLI test loads via `@guren/core` (routers, route definitions) is the *built* server, however fresh the source is.
- **`git stash` does not make a checkout clean.** `dist/` is untracked, so stashing leaves stale artifacts in place. When a test fails only on one machine, rebuild before bisecting: `bun run build:clean` (or `bun run build:<pkg>` for a targeted check).

## CI Environment

- **Never use `bunx guren` in CI.** The `guren` package is not on npm. Use `bun packages/cli/src/bin.ts` directly. A smoke's `['bunx', 'guren', …]` passes locally only because the temp app's `file:` link to packages/cli happens to provide a `.bin/guren` — the link CI cannot be trusted to have. `audit:workspace-scripts` covers three scopes: workspace `package.json` scripts, spawn shapes under `scripts/**/*.ts` (argv arrays, `$` shell templates, `exec`/`spawn` calls), and command lines in `scripts/**/*.sh`. It does **not** read `.github/workflows/*.yml` shell steps or `packages/*/src`, so the rule is wider than the gate there.
- **Vite route-types plugin resolves `@guren/cli/bin` and spawns it with `bun` directly** (no `bunx guren`, which 404s in this monorepo). It still skips generation when `process.env.CI` is set — CI runs codegen as its own step, and watcher-triggered regeneration during E2E would be nondeterministic.
- **E2E webServer in CI uses `bun run e2e:server`** — not `bun run dev` (triggers codegen) and not `bun run dev:server` (runs under `bun --hot`, so the server would reload mid-test if anything touched a watched file).
- **`bun run --cwd` with `bunx` can resolve from npm instead of local.** Use `cd dir && bun ...` or direct paths.
- **A gate that assumes the port it asked for is green on CI for a reason that does not hold locally.** The scaffolded `bin/serve.ts` walks the port forward (dev mode, up to +19) when the one it was handed is busy, and announces that only on stderr. A harness that addresses the port it *requested* therefore reaches whatever else is on it — a server leaked by an earlier run, or a second smoke beside it — while its own app sits one port up; the `/health` probe passes against the stranger, so every later assertion describes an app that was never under test. CI never sees this: fresh container, and the driver runs are sequential steps in one job. **Read the port the app reports binding and address that** (`smoke:golden-path` step 16 parses the startup banner). Checking instead for the *absence* of the "port is in use" warning fails open — it silently stops protecting the moment that warning is reworded, and the warning may not even be written yet when a stranger answers first. **Corollary: when a gate is red only on a developer machine, check what else is listening before reading the assertion literally.**
- **Pin the bind address as well as the port, and address that same literal.** `localhost` resolves to `::1` first on macOS while a `0.0.0.0` bind is IPv4-only, so name-vs-bind mismatches let a request reach a listener you did not mean. An ambient `HOST` moves the bind out from under a hard-coded URL too.
- **`$(curl ...)` under `set -e` dies before your error message runs.** A curl that cannot reach the server exits non-zero, the command substitution fails the assignment, and errexit kills the script — so the assertion's own diagnostic never prints and the run ends on a bare `exit 7`. Capture with `|| rc=$?` and report the code. The inverse is what makes body assertions lie: a 302 or a 500 gives curl exit **0** with a body that merely lacks the needle, so a substring check blames the app for a status it never inspected. Check the status before the body.

## Templates vs. Published Packages

- **A template can use an API that does not exist yet for its users.** `packages/create-app/templates/**` is application code that resolves `@guren/*` from **npm**, not from this checkout. Adding an export in `packages/orm` and using it from a template in the same PR ships templates that only build after the next release.
- **Nothing in the normal gate can see this.** Root `typecheck` skips templates (`packages/create-app/tsconfig.json` excludes `templates`). No generated file is left in the worse class this bullet used to name: `config/database.ts`, `drizzle.config.ts` and the fallback `db/schema.ts` were each emitted as *strings* from `packages/create-app/src/blueprints.ts`, so no tsconfig anywhere covered them; all three now ship as real per-driver sources under `packages/create-app/templates/database/<driver>/`, copied verbatim and parse-gated by `tests/database-config-template.test.ts` and `tests/database-schema-template.test.ts` — but still excluded from every typecheck like the rest of the templates, for the npm-resolution reason above. Keep it that way: a new scaffolded file belongs under `templates/`, not in a template literal. `smoke:starter` and `smoke:starter:packed` both rewrite the app's `@guren/*` deps to local builds, so they typecheck against unreleased code too. The create-app tests assert the generated text, not that the symbols exist.
- **`bun run smoke:starter:npm` is the one check that installs from the registry.** It is on the scheduled `Published Package Drift` workflow rather than in CI, because it is *correctly* red between a template-facing change and the release that publishes what the template needs. Cutting that release is the fix — not editing the template back to an older API. **A drizzle pin bump reads the same way:** the `@guren/*` ranges only ever move at `changeset version`, but `packages/orm`'s `drizzle-orm` pin can move in an ordinary PR, and until that release ships, npm's `@guren/orm` still installs the old copy beside the template's new one.
- **A caret range does not follow a major, so "just release it" is not automatic.** A template stranded on an older major keeps installing that line forever, while any `@guren/*` package still on a minor line *is* followed — which is how one app ends up with two copies of the ORM, a runtime `database has not been configured` rather than a type error.
- **Template dependency versions are generated, never hand-edited.** `bun run sync:template-deps` writes the `@guren/*` ranges from the workspace versions and the drizzle pins from `packages/orm/package.json`; `version-packages` runs it right after `changeset version`, the first moment the new numbers exist. `audit:template-deps` asserts the same invariant in CI. Any release that moves a `@guren/*` version must also bump `create-guren-app`, or `changeset publish` ships no tarball carrying the new ranges — the sync script fails the release if that happens.
- **`gurenPlugin.compatibility` is the one version claim nothing writes, and changesets will happily contradict it.** Changesets *does* maintain `@guren/*` dependency ranges, including for a package with no changeset of its own: when a dependency crosses a major, a dependent whose range no longer admits it is pulled into the release plan and its range rewritten (`^1.4.0` → `^2.0.0`). Verified directly against `changeset version`, so do not assume a stale-looking range will stay stale. What changesets cannot touch is `gurenPlugin.compatibility` — it has no idea the field exists. So the hazard is not a range rotting on its own; it is the release where the dependency gets rewritten to `^2.0.0` while `compatibility: ">=1.0.0 <2.0.0"` stays put. That manifest installs cleanly from npm and *then* refuses to load, because `guren plugin` throws on the mismatch (`packages/cli/src/plugin.ts`, unless `--ignore-compatibility` is passed). Workspace linking hides all of it — build, typecheck and test stay green whatever the ranges say. `audit:plugin-compat` runs in CI and again inside `version-packages`, right after `changeset version` creates the contradiction. Note the loader treats an *absent* `compatibility` as "no claim" and passes it; the audit is stricter and requires first-party plugins to declare one. It exits 2 rather than passing on a range shape it cannot reason about (a non-caret/tilde/exact dependency, a union `compatibility`) — an unavailable check is not a green one.
- **Which packages a smoke resolves from the checkout is derived, never listed** — `scripts/smoke/local-packages.ts` owns that rule and the vendoring that applies it, for all three smokes including the bash one. Adding a package to a hand-kept copy of the list is how `@guren/testing` came to be installed from npm by two gates, which then verified a *published* copy for releases. The module header has the rest; the one trap it cannot make structural is that a template's `package.json`, and the fixture manifests the smokes rewrite, are read by more than one gate — `sync-template-deps.ts` reads the same template set through `templateManifests()`.
- **`@guren/core` is not on the release train's version.** The repo tags releases after `@guren/server` (v2.2.0), but core deliberately sits on its own line — 1.5.1 at that same tag. A "v2.x workspace" therefore says nothing about what `^1.4.0` or `>=1.0.0 <2.0.0` resolve to; check `packages/core/package.json` before concluding a core range is stale.
- **The version core sits on is independent; the *bump type* is not.** `packages/core/src/index.ts:1` is `export * from '@guren/server'`, so a symbol server removes is a symbol core removes — but `changeset version` never promotes a dependent bump to match its dependency, it only rewrites the range. That is how server 2.0.0's RFC 0006 removals shipped as core **1.5.0**, a minor, straight through every `^1.4.0`. `audit:core-semver` reads the pending `.changeset/*.md` and fails a plan that majors `@guren/server` without majoring `@guren/core`; it runs in CI and again at the head of `version-packages`, before `changeset version` consumes them. Bump core even when the break looks confined to a subpath: the only server surface that genuinely cannot reach core is `/mcp` and names outside the `lambda.ts`/`redis.ts` allowlists, because `runtime.ts` and `vite.ts` are wholesale `export *` like the root barrel. Over-bumping costs one deliberate revision; under-bumping is delivered silently by a caret.
- **`fixed: [["@guren/server", "@guren/core"]]` is not the fix.** The grouping is bidirectional and only one of its directions is true: server major ⇒ core major is semantically forced by the re-export, core major ⇒ server major is a version with no content for anyone depending on `@guren/server` directly. A fixed group also snaps to its highest member, so adopting it crosses core's major line inside whatever release comes next, however small. Both halves were measured against `changeset version` rather than read off the docs — the module header of `scripts/smoke/core-semver-audit.ts` has the numbers.

- **`packages/cli/templates/scaffold/**` typechecks against workspace source, like every local gate.** `typecheck:templates` proves the static scaffold templates compile — against `packages/*/src`, not against the `@guren/*` a scaffolded app installs from npm. A template adopting an API added in the same PR stays green here and in every smoke that vendors local builds; only `smoke:starter:npm` (scheduled, correctly red until the release ships) sees it. Same story as `create-app/templates` above. Also: root `tsc --noEmit` deliberately excludes this tree (it needs the `tsconfig.templates.json` overlay with the `tests/fixtures/scaffold-typecheck/` companions), so "root typecheck is green" says nothing about the templates — the root `typecheck` *script* chains `typecheck:scaffold-templates` for that.

## Security Defaults

- **`X-Testing-User` header is gated behind `GUREN_TESTING` env var.** TestApp sets this automatically. Never trust this header in production.
- **MCP endpoint requires `GUREN_MCP=1` to mount.** Features that expand attack surface (debug endpoints, code generation APIs) must be opt-in, not opt-out. Security protections (CSRF, headers) are the opposite — enabled by default.
- **The dev-endpoint gates read `process.env.NODE_ENV` with no optional chaining, on purpose.** `isMcpEndpointEnabled()` / `isDocsViewerEnabled()` are the only thing standing between a deployed app and these endpoints, and all three deploy plugins settle that branch at bundle time with `--define 'process.env.NODE_ENV="production"'`. A define matches **one exact expression**: `process.env?.NODE_ENV` is a different expression, so adding `?.` silently converts the production gate back into a runtime read — and `plugin-cloudflare`'s own comment explains why that is not equivalent (wrangler `vars` are not guaranteed to reach `process.env` before the module graph evaluates). The `typeof process` check already covers every runtime without `process`; there is no runtime the framework supports where `process` exists and `process.env` does not. A source-level test in `packages/server/tests/{mcp,docs-viewer}/endpoint.test.ts` pins the form, because nothing at runtime can tell the two apart.
- **The MCP endpoint is CSRF-exempt and guards its own access.** MCP clients POST JSON-RPC without ever fetching an `XSRF-TOKEN`, so `createCsrfMiddleware` skips that one path while `isMcpEndpointEnabled()` holds. `createMcpAccessGuard()` replaces it and has to stop **two** classes of caller: browser pages (rejected unless the `Origin` is loopback) and non-browser clients (rejected unless the socket peer is loopback). The second half is not optional — templates bind `0.0.0.0`, `Host` is trivially forged so host authorization does not help, and a client that sends no `Origin` is otherwise indistinguishable from a local agent.
- **`createLoopbackGuard()` fails closed: no peer address means deny.** Absent signals used to mean "allow" on both checks, so a caller with no `Origin` on a runtime that reports no peer passed both — the exact shape of a remote `curl` against a host that serves via `app.fetch()` rather than `Application.listen()` (`@guren/plugin-vercel` does this even though Bun is present). The peer must now be *positively* loopback. A loopback `Origin` does **not** satisfy it: `Origin` is a negative filter attesting that a *browser* saw a cross-site request, and every non-browser client sets it with one flag. The escape hatch for genuinely peer-less runtimes is `GUREN_ALLOW_UNVERIFIED_PEER=1` (same `GUREN_*` / `=== '1'` shape as `GUREN_MCP`), and the 403 body names it. Tests that drive these endpoints in-process must pass a fake `{ server: { requestIP } }` env — `Application.listen()` supplies the real one, so `bun run dev` is unaffected.
- **Rate limiting default key uses `server.requestIP()` (Bun only).** Falls back to shared per-route bucket with console warning. Docs tell users to supply custom `keyGenerator` in production.
- **CORS defaults to same-origin** (no `Access-Control-Allow-Origin` header). Users must explicitly set `origin: '*'` if needed.
- **Host authorization is dev-only** in templates (`process.env.NODE_ENV === 'production' ? false : { ... }`).

## Auth Middleware Ordering

- **Auth context resolves its session lazily** (at first guard use, not attach time), so `attachAuthContext()` may sit anywhere in the chain — including before session middleware. The session middleware only has to run before an auth *method* is called.
- **For apps without `options.auth`**, the fallback `attachAuthContext` is attached in the `Application` constructor, so `app.use(requireAuthenticated())` before `boot()` works (#13).
- **With `options.auth`**, `AuthServiceProvider.register()` mounts session middleware and attaches its own auth context as before.

## Template Dependencies

- **`drizzle-orm` and `drizzle-kit` in the templates are generated too, from `packages/orm/package.json`.** Bump the ORM's exact pin (under `dependencies`, not peerDeps) and run `bun run sync:template-deps`; `audit:template-deps` fails CI if you don't. The rule lives in `packages/cli/src/drizzle-pins.ts`, shared with `guren upgrade`, which applies the same alignment to an installed app. Templates pinning a different `drizzle-orm` than the ORM installs is how a scaffolded app gets two copies in one process.
- **The one drizzle case still left to a human:** `drizzle-kit` has no upstream declaration to follow, and the two packages have never shared numbers on their stable lines, so the sync checks the companion release exists on npm before writing it. When it doesn't — or when npm can't answer — both the sync and `guren upgrade` say so and leave the pin alone rather than failing; pick the matching `drizzle-kit` release yourself. The two refusals the sync *does* fail on are the ones fixable here: a template specifier naming a location (`workspace:*` and friends can never ship to npm) and a `packages/orm` that stopped pinning one exact `drizzle-orm` version, which silently switches the whole rule off.
- **API-only template has no Vite, React, or Inertia.** Force SPA mode in CLI (`blueprint === 'api'` → skip SSR).
- **Default template always calls `configureOrm()`** even without migrations (models need a DB connection).

## Dockerfile / Deployment

- **Use multi-stage builds.** Builder stage needs devDeps for Vite/TypeScript. Production stage uses `--production`.
- **Entrypoint is `bun bin/serve.ts`**, not `bun run start` (no `start` script exists in templates).
- **Copy runtime dirs explicitly**: `bin/`, `src/`, `app/`, `config/`, `routes/`, `public/`, `db/`, `.guren/`.

## Serverless Bundling (Vercel / Lambda)

- **`bun build` inlines `process.env.NODE_ENV` at bundle time** (defaults to `"development"`, regardless of minification). Runtime `NODE_ENV=production` cannot override it. Always pass `--define 'process.env.NODE_ENV="production"'` when bundling server entrypoints for deployment (`@guren/plugin-vercel` does this).
- **Never bundle app code with identifier mangling** — no bare `--minify`, no esbuild/oxc `minify: true`. Guren keys durable records on class names: the queue registry stores `JobClass.name` in every queued message, notifications persist `constructor.name` as their `type`, and `HttpException` reports `this.constructor.name`. Mangled, records written by one deploy stop resolving after the next. Use `--minify-whitespace --minify-syntax` (or `minify: { whitespace: true, syntax: true, identifiers: false }`). `--keep-names`/`keepNames` is **not** a substitute: as of Bun 1.3.14 it is accepted and silently leaves class names mangled. With rolldown/tsdown, `mangle: false` is not enough either: `compress` inlines single-use classes as anonymous expressions (`.name` becomes `""`); use `minify: { compress: { keepNames: { class: true, function: true } }, mangle: false }` (verified against rolldown 1.2).
- **Cold-start work must be measured on a bundle, and against `dist`.** Two traps, both of which produce a confident wrong number. First, running the app with `bun run` loads the module graph file by file, so anything that only lets a *bundler* drop code — `sideEffects`, an import moved behind a branch a `--define` settles — is invisible by construction; a flat result there means the profiler cannot see the change, not that the change did nothing. Measure by bundling with the deploy plugin's own stub set and options, then timing the bundle's cold start. Second, in this monorepo `@guren/*` resolve to `packages/*/src` through the root tsconfig paths, so an in-repo bundle measures a src (or mixed src+dist) graph that no installed app has. Build a fixture outside the workspace holding each package's `package.json` + `dist`, and confirm with `import.meta.resolve` that all three land on `dist/index.js`. Getting that fixture subtly wrong is easy and quiet: giving the copied packages their own `node_modules` lets `@guren/server` resolve back into the checkout, which reported a real -40.9% bundle win as -0.14%. Flatten third-party deps to the fixture's top level instead.
- **SSR bundles must be self-contained on serverless.** Function directories ship without `node_modules`, so externalized `react`/`@inertiajs/react` imports fail at runtime and Inertia silently falls back to CSR. The Guren Vite plugin defaults `ssr.noExternal: true` for SSR builds — don't re-externalize deps in `.guren/ssr` unless the deploy target has them installed.

## TypeScript 7

- **`typescript` ships no JavaScript compiler API** — `require('typescript')` throws. Anything that needs to parse or type-check drives the `tsc` binary (`packages/cli/tests/helpers.ts` `checkTypes` / `resolvedCompilerOptions` and `scripts/check-build-configs.ts` via `tsc -p`, `tsc --showConfig`) or parses with `@babel/parser` (`scripts/fix-dts-extensions.ts`). A new dependency that imports `typescript` at runtime (an old `rollup-plugin-dts`, `ts-morph`, `typescript-eslint` below its TS 7 line) fails at first use, not at install.
- **`rootDir` defaults to the tsconfig directory and is enforced under `noEmit` whenever `rootDir` or `outDir` is explicit.** The root `paths` pull sibling packages into every program, so no `packages/*/tsconfig.json` sets `outDir`/`declaration` any more (tsdown passes its own `--outDir`/`--rootDir`; only `packages/server/tsconfig.build.json` emits, and it clears `paths`). A gate that compiles files from two trees must likewise leave `rootDir` unset. `baseUrl` is gone (TS5102): `paths` resolves from the tsconfig directory, so write targets with `./`.
- **The native declaration emitter writes out-of-`rootDir` files beside their sources.** tsdown runs `tsgo --emitDeclarationOnly --outDir <tmp> --rootDir <package>`; any file the program reaches *outside* that package (a sibling pulled in by the root `paths`) lands as `src/*.d.ts` next to the sibling's source, not in the temp dir, silently (`--noCheck` hides TS6059). One `bun run build cli` used to leave 260 such files across four packages. Every package whose sources import a sibling therefore points tsdown at a `tsconfig.build.json` that layers `tsconfig.build-base.json` (`paths: {}`) over its own config, resolving siblings through `node_modules` to their built declarations; the build order guarantees those exist. `scripts/build-packages.ts` fails a build that leaves untracked `packages/*/src/**/*.d.ts` behind — fix the config, do not add them to `.gitignore`. The other half of the same trade: with `paths: {}`, a sibling the package never *declared* is unresolvable, and `tsgo --noCheck` turns every type inferred from it into `any` rather than failing. `bun run typecheck:build-configs` (part of `typecheck`) runs `tsc -p tsconfig.build.json --noEmit` per package with checking on so that drift fails; a genuinely optional sibling reached only through a dynamic `import()` is **declared as an optional peer** (`peerDependencies` + `peerDependenciesMeta.optional`), which is what makes `paths: {}` resolve it to the sibling's real `.d.ts` instead of leaving it `any` — `@guren/cli` → `@guren/openapi` and `@guren/testing` → `@guren/core` are the two. Neither npm nor bun installs an optional peer automatically, so a user's install is unchanged, and a wide range (`>=1.3.0`) keeps changesets' `onlyUpdatePeerDependentsWhenOutOfRange` from starting a release chain. The price is a real edge for the topological sort: `bun run build:list` must show the sibling building *first*, or `paths: {}` finds no `dist/index.d.ts` and you are back to silent `any` — and a peer that would close a cycle cannot be declared at all (that is what `deps.neverBundle` is still for: `@guren/server` → `@guren/cli`). Declaring it also makes it external to the bundle by default, so the matching `neverBundle` entry goes away with the `@ts-ignore`. Subset builds (`bun run build cli`) resolve siblings to whatever `dist/` is on disk — the gate, not the build, is what catches a missing or stale one.

## ESM Compatibility

- **No `require()` in ESM packages.** Use top-level `import` or dynamic `import()`. Bun tolerates `require()` but Node ESM does not.
- **Keep `"type": "module"` and spread `tsdownPreset` (`scripts/tsdown-preset.ts`) in every tsdown config.** It carries `fixedExtension: false` (every `exports` map names `dist/*.js` / `dist/*.d.ts`; tsdown otherwise emits `.mjs` / `.d.mts` on node) and `target` — the header explains both once.

## E2E Tests

- **E2E needs `NODE_ENV=production` for Vite assets but runs over HTTP.** Two CI-specific issues: (1) `VITE_DEV_SERVER_URL` in `.env` forces dev-mode asset serving even with production NODE_ENV — remove the line in CI setup. (2) Cookie `Secure` flag must be disabled when `CI` is set (see `examples/blog/src/app.ts`), otherwise Inertia XHR POSTs fail (CSRF/session cookies rejected over HTTP).
- **Use `storageState` for authenticated tests** — login once in setup, share session across all tests.
- **Avoid asserting specific post titles in lists** — pagination may push them off page 1.
- **Use `page.waitForLoadState('networkidle')` after Inertia navigations** in CI.

## Lint

- **`bun run lint` is oxlint with type-aware rules, and it needs Node on PATH.** The `oxlint` bin is a Node shim (`#!/usr/bin/env node`), and JS plugins go through Node's module loader — which is also why `scripts/lint/await-async-assertion.js` is JavaScript: a `.ts` plugin fails to load. Type information comes from `oxlint-tsgolint` (typescript-go), the only type-aware linter that runs on the `typescript` 7 this repo pins; typescript-eslint needs the JavaScript compiler API that package no longer ships.
- **`typescript/no-floating-promises` cannot see a bare `expect(...).rejects` on a `bun:test` file.** bun-types declares `rejects: Matchers<unknown>` and `toThrow(): void`, so the promise the matcher returns is typed away and the rule stays quiet; 22 such assertions shipped before one was noticed (#656). oxlint's `jest/valid-expect` is syntactic but only recognises `expect` imported from jest or vitest, not from `bun:test`. `guren/await-async-assertion`, a JS plugin under `scripts/lint/`, is the syntactic and import-agnostic rule that closes the gap. The same lie cuts the other way: `typescript/await-thenable` would flag every *correctly* awaited `bun:test` assertion (281 at the time), so it stays off.
- **The dangerous auto-fixer rewrites rest-sibling destructuring.** `oxlint --fix-dangerously` turned `const { dependencies, devDependencies, peerDependencies, ...rest } = manifest` into `const { devDependencies, ...rest } = manifest`, which changes what `rest` holds. `no-unused-vars` runs with `ignoreRestSiblings: true` so those names are never reported, and `bun run lint:fix` applies only the safe fixes.
