Resolve a `file:` URI filename to a path in `createSqliteDatabase()`, instead of concatenating it.

The sqlite driver `mkdir -p`s the database's parent directory before opening it, and it computed that directory with `dirname(resolve(dbPath))`. `resolve()` has no notion of a URI, so `file:///var/tmp/app.db` is taken as a *relative* name and the driver prepares `<cwd>/file:/var/tmp/`. Running the framework suite deposited one `file:/var/folders/…/guren-sqlite-XXXXXX/` tree into the repository per run. It is untracked, so `git status` says nothing and no build, typecheck, or test gate reads it; only `git clean -nd` reports it, as `Would remove file:/`.

This is the same class of defect #438/#440 addressed for connection strings, on the other side of the guard they added. That change narrowed the rejection to the *intersection* — a scheme with an authority, `file:` excluded — precisely because `file:` is sqlite's own URI scheme and names a file rather than a server. The narrowing is unchanged here. What it left standing is that a legal `file:` URI still has to be *parsed* before it can be used as a path.

**The driver now does that parsing itself, and hands `new Database()` the plain path.** That is the part worth reading closely, because the obvious smaller fix — stop the mkdir mangling the URI, let sqlite parse it — is wrong, and the reason was measured rather than reasoned about:

**URI filenames are a compile-time option (`SQLITE_USE_URI`), and the builds Bun runs on disagree.** Bun on macOS goes through the system libsqlite3, which has it on: `file:sub/x.db` creates `sub/x.db`. Bun's own Linux build has it off, and takes the same string as a filename that literally starts with `file:`. So the stray tree was never one defect: on macOS it was empty and the database was correct, while **on Linux the tree held the actual database** — the mkdir was the only reason those opens worked at all. A fix that merely stopped creating it turned Linux CI red with `SQLITE_CANTOPEN`, which is how this was found; the local suite was green on all of it.

Resolving in the driver is what makes one filename mean one file on every host. The rules followed are sqlite's (https://sqlite.org/uri.html), not the WHATWG URL parser's, which matters in a way that is easy to get backwards: `new URL('file:local.db')` yields `/local.db`, an absolute path at the filesystem root, where sqlite resolves that URI against the cwd — so parsing these through `node:url` would have moved the mkdir from the wrong directory to a worse one. An authority of `localhost` is accepted alongside the empty one; any other authority, and the empty-filename forms, resolve to no path at all, and the original string is handed to `new Database()` to be refused there with no directory created on the way.

**One deliberate break: a `file:` URI carrying query parameters is now rejected** with an error naming them. A path cannot carry `?mode=ro`, and there is no portable behavior to preserve — that URI enforces read-only on macOS today and creates a file with a `?` in its name on Linux. Silently dropping the query would hand back a writable database where one host used to give a read-only one, so it stops loudly instead. A `#fragment` is still dropped silently, the way sqlite drops it. The in-memory forms (`:memory:`, `''`, `file::memory:…`) are passed through untouched and keep whatever host-specific behavior they have today.

**The hot-reload key is fixed with the same resolution,** because it read `resolve(dbPath)` too: under `bun --hot`, `file:///data/app.db` and `/data/app.db` are one database but were keyed as two, so a reload that merely restyled the filename left the first handle open instead of replacing it.

Eight regression tests in `packages/orm/src/sqlite.test.ts`, each shown to fail against the implementation it guards. The load-bearing one, `should create the directory the URI names, not one named after the URI`, targets a directory that does not exist yet and asserts both halves — the database file was created *and* no `file:` tree was — so it reds both for the concatenating version and for the tempting shortcut of skipping the mkdir whenever the filename is a URI. The pre-existing `file://` and `file:local.db` cases gain the absence and *location* assertions they were missing; asserting where the file lands is what makes them portable, since a host that does not parse URI filenames opens one named literally `file:local.db` and reports success. The rest cover percent-decoding in a directory segment, the `localhost` authority, the rejected query, the ignored fragment, and the hot-reload key.

One property is not observable on a URI-parsing host: opening the resolved path rather than the original string is indistinguishable on macOS by construction, because both name the same file there. That row is verified by CI on Linux, where it was the failure.
