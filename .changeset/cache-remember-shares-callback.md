`remember()` and `rememberForever()` on a store from `CacheManager.store()` share one callback between the calls in a process that miss the same key with the same TTL while it runs: the callback runs once, and every one of those callers receives the same result object or the same error. `rememberForever` counts as a TTL of its own, so a call never stores a TTL it did not ask for. Hits are read before joining and are not shared, so each concurrent hit still receives what `get()` returns. A callback that throws caches nothing, so the next call retries. Tagged caches, including one built with `new TaggedCache(store, tags)`, share by the key after tag resolution and store the result under the namespace they read, so a `flush()` while the callback runs no longer leaves its result under the new namespace. Only calls through the same store instance share. A call that arrives 10 seconds or more after the running callback started runs its own instead of waiting. `set`, `delete`, `setMany`, `deleteMany` or `clear` through the same store make later misses start a new callback; the running callback still stores its result when it finishes. A store constructed and called directly (`new MemoryStore()`) is unchanged. On the file and Redis stores, callers that miss together now share one object where each used to receive its own copy, so code that changes a remembered value in place should copy it first.
