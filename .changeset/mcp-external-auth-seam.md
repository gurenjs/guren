Accept an externally verified principal at the App MCP endpoint, over a request-identity seam (RFC 0016 §7).

Behind an OAuth provider — a Cloudflare worker built with `guren cloudflare:build --mcp-oauth` — the provider has already validated its own access token before the request reaches the app, and hands the grant's `props` to the protected handler. The endpoint needed a way to be told "this caller is already verified, as this principal, with these scopes" that a network caller cannot assert.

**The channel is object identity, not a header.** `presentExternalMcpAuth(request, auth)` registers the grant in a `WeakMap<Request, ExternalMcpAuth>` and returns the *same* object, which the caller must dispatch; the endpoint consults the map before any bearer machinery. This is the pattern RFC 0017 §2 specifies for its durable principal handoff, adopted here first: a value keyed on object identity has no wire representation to forge, needs no `AsyncLocalStorage` (so it behaves identically on workerd and Bun), and is collected with the request. A rebuilt or cloned `Request` does **not** carry it — that is the security property, and it is tested in both directions.

**Fail-closed both ways.** A seam hit skips the token store and `verifyApiToken` entirely; everything downstream — the scope gate, the rate-limit key, `AgentToolInvoked` / `AgentToolDenied`, `surface: 'mcp'` — flows exactly where the bearer-derived values do. A miss takes the unchanged bearer path, so an app that never presents the seam cannot tell this release from the last. New `mcpPlugin({ auth: 'external' })` declares that every request arrives seam-authenticated: a request without it is refused 401 and never falls through to bearer, and the app needs no `ApiToken` store at all, because the store is only ever consulted to verify a bearer.

**Two narrowings on the seam surface, both deliberate.** The rate-limit key is derived from the principal rather than a token id — coarser, which for a floor can only limit more. And no `Authorization` is forwarded into the dispatched request: the inbound bearer belongs to the authority in front of the app, which the app's own token guard has never seen. So the scope gate and the route's policies still run, but a route behind `requireApiToken` answers 401 to an OAuth-authorized caller until the auth context itself consults a principal seam (RFC 0017 §2).

New subpath export `@guren/plugin-mcp/oauth` carries `presentExternalMcpAuth`, `mcpOAuthPropsToAuth` and their types, so a deployment that never fronts an OAuth provider does not pull them in. `mcpOAuthPropsToAuth` resolves RFC 0016's Open Question 2: `props` are `{ userId: string | number, scopes: string[] }` from a session-authenticated consent flow, mapped to `{ kind: 'user', id: userId, abilities: scopes }`, with `userId` passed through in whichever type it arrived as — coercing in the glue and nowhere else is how a policy lookup silently misses. A shape it cannot recognize answers `null` and the caller refuses the request. A dist-level test asserts both built entries share one `WeakMap`; two would be a seam that never hits, with every source-level test green.
